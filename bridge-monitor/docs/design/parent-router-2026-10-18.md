# GPT-side Bridge Monitor router — design for review

## Purpose and evidence

The router gives GPT/Codex one explicit Bridge Monitor entry point for bounded work. It first measures whether Skynet/Qwen could complete selected work before a paid Claude worker is invoked. A later, separately reviewed canary may deliver a Qwen result only after an independent check passes; every other outcome continues to the approved paid worker. The first implementation is **shadow only**: Claude remains authoritative, and no Qwen candidate is delivered to the parent.

The read-only assessment in “Assess Bridge Monitor routing” found 30 observed leaf work items, 30 Sonnet executions, 20 Skynet dispatches, and no independent live evaluation records. The current path invokes Sonnet before optional Qwen, so a retained Qwen contribution is not an avoided Sonnet call. In the 12-question offline holdout, Qwen passed nine exact checks, but the candidate path took 35.040 seconds versus 32.611 seconds direct; known answers made those checks possible. The two retrospective code-fix probes are too small to predict real fix quality. The natural test-backed code-fix cohort has 0/30 attempts. These measurements justify an instrumented shadow route, not a live quality gate or a paid-savings claim.

## Scope and entry point

Add an opt-in parent MCP operation, provisionally `route_work`, beside `delegate_claude`. It accepts the existing scoped task packet, original prompt, approved paid model and budget, an output-contract identifier, and an optional reference to a pre-registered verifier bundle. The router returns a durable call/status identity and the authoritative paid result in shadow mode. Existing `delegate_claude` and Claude-to-Qwen delegation remain usable and unchanged. The router does not transparently intercept every Codex message or the other registered bridges; reports state the number of router-submitted tasks and never imply account-wide traffic coverage.

The first supported candidate class is a small, single-file Python fix with a complete-module output contract, a captured broken baseline, and trusted tests fixed when the natural task arrived. The verifier reference resolves to a hash-pinned project-local snapshot of that baseline, tests, original task reference and capture time. The parent may submit tasks without a verifier reference, but they go directly to Sonnet with a recorded reason. Arithmetic with a reliable calculator, broad code reasoning without an oracle, ambiguous architecture, and tasks requiring unavailable tools are not Qwen-first candidates. The RX 7900 XT is not a router backend in this version; the Skynet agent and pinned Qwen profile remain the only local candidate.

Use one logical task and work-item identity for the parent's request and both comparison arms. Record distinct call, attempt, model-execution, decision, result and evaluation IDs. The parent routing decision is separate from a later Claude-to-Qwen child decision. The selected policy version, model profile/digest, verifier version and task snapshot are pinned at admission. A policy reload affects only later admissions; a withdrawn verifier or safety restriction is rechecked before local dispatch. Every operational number that may reasonably change—eligibility categories, sampling, queue and execution deadlines, token budgets, verifier limits and retention—comes from reviewed configuration. Independent verification, scope checks and the prohibition on unverified local delivery are invariants, not configurable bypasses.

## Shadow data flow and safety

On `route_work`, capture the original request and a parent-router decision before any worker dispatch. Check scope, category, output contract, baseline/test provenance, context and token budget, agent profile, capacity, deadlines and capture health. A pre-dispatch rejection selects Sonnet directly, records the exact reason and does not create a Qwen job. Missing or uncertain facts fail closed for Qwen eligibility. Existing paid admission rules still apply; a router decision cannot grant extra source access, budget or capability.

For an eligible shadow task, invoke Sonnet through the existing paid coordinator. Its result remains the only result delivered to GPT. Capture the exact input before the paid call, then run one Skynet candidate as a bounded shadow attempt using that same task and broken source. The shadow prompt contains neither Sonnet's answer nor the host-held expected outputs. Shadow processing may finish after the paid result and must not delay its delivery. Do not launch a duplicate paid call merely to complete a comparison; if the real paid answer cannot be checked against the same output contract, mark that pair non-comparable. A later passing paid replacement may serve as a reference only after the baseline and tests have been shown to distinguish broken from repaired behavior. Preserve the original pre-solution task and test snapshots.

Run candidate code only through the existing digest-pinned isolated verifier. Record parse, import, test and resource-limit failures separately. A valid JSON wrapper, Qwen self-confidence, or Claude-reported acceptance cannot substitute for verification. A Qwen timeout, uncertain accepted job, verifier outage, capture gap or cancellation cannot deliver a local answer or trigger an automatic Qwen retry. Preserve uncertain remote ownership and capacity under the existing reconciliation rules; shadow work may fail without altering the already selected paid answer. Future live canary behavior is outside this implementation and requires a separately reviewed policy and rollback.

## Auditable decisions, results and analysis

Every router submission produces an audit chain: original and effective prompt content/hashes; source and test snapshot references; task origin and category; decision stage (`parent_router` or `claude_child`), mode (`production` or `shadow`), eligibility facts, rule IDs, policy hash/version, reason and selected destination; queue/dispatch/attempt state; requested and reported model/digest; raw and parsed response; verifier version, outcome and evidence; paid fallback or correction; parent acknowledgment and final resolution. Record timestamps for admission, queue, model load, inference, polling, verification, delivery and later correction where observed. Store provider-specific input, cache-read, cache-creation and output token categories with provenance and coverage. Keep list-cost estimates, subscription allowance usage and billed charges distinct; missing values remain unknown. Corrections or reassessments append a superseding record with their own actor, time and reason; they do not silently rewrite the original judgment. Hashes detect accidental drift but do not prove a mutable local receipt was never deliberately changed. Do not copy secrets into decision facts or reports. Existing content access controls and retention apply to full prompts and responses.

Use the existing event, content, decision, result, evaluation, usage and configuration records where they fit; extend their contract only for the router stage, execution mode and verifier evidence needed for reliable queries. A shadow candidate is retained as a result with **no delivery timestamp or `result.delivered` event**. Production metrics must exclude shadow dispatches even when they share the observed work-item ID. Extend the query predicates and metric definition version before emitting shadow dispatch events, and provide a separate shadow cohort view. The default dashboard continues to count only actual production dispatches as “routed.” An explicit paid decision made before any local dispatch counts as “not routed”; a local dispatch followed by paid fallback remains routed. A shadow attempt is neither of those production outcomes.

The dashboard provides a per-task router audit and a filterable shadow cohort report, showing both the decision made and the later outcome so optimization can examine false exclusions, Qwen failures, paid corrections and time lost before fallback. Analysis groups failures by task type, output contract, model and prompt version, guidance, context size and reason. Distinguish wrong behavior from format failure, timeout, infrastructure failure and missing evidence. Show attempted-task denominators, independent evaluation coverage, parent-reported judgments and subsequent corrections separately. A shadow comparison may estimate avoided paid **worker calls**; it cannot claim net billed savings without parent usage and a valid billing basis. No outcome automatically rewrites a gate or promotes a candidate to live routing. Any later rule proposal requires reviewed evidence, an activated config hash and rollback history.

## Delivery sequence and exit checks

1. **Accounting contract.** Add router-stage and execution-mode attribution to the existing audit path and a task-level comparison query. Confirm with synthetic events that shadow calls never inflate production routed, not-routed, takeover or worker totals; incomplete usage and evaluation remain unknown. Distinguish a verified shadow candidate from a delivered local result, and show router coverage beside other bridge traffic rather than claiming complete observation.
2. **Opt-in shadow ingress.** Add `route_work` and reuse paid admission, Skynet leases, telemetry capture and the isolated code verifier. Test eligible, ineligible, format-failed, wrong, unavailable, timed-out, cancelled and uncertain cases. Confirm one authoritative paid delivery, no shadow delivery, no duplicate local dispatch and no extra paid comparison call. Existing `delegate_claude` and child delegation tests still pass.
3. **Natural cohort.** Freeze the prompt, model and verifier protocol before the first qualifying task. Register each distinct natural test-backed fix when it arrives and retain every attempted or interrupted case. Reconcile provenance against the original task list. At 30 attempts with no unresolved receipts, report verified local candidates, paid quality, failures, worker calls, end-to-end latency, corrections, model/usage coverage and cost basis. This is a review trigger, not automatic canary authorization.
4. **Decision after evidence.** If independently verified quality, latency and paid-use evidence justify a narrow category, write a separate canary proposal with a small configurable share, automatic paid fallback, monitored rollback and a reviewed failure gate. If the data do not justify it, leave paid routing in place. Consider the RX 7900 XT only after matched warm/cold and contention measurements show a useful capacity or latency gap.

All implementation work stays under `C:\AI\bridge-monitor`. No source under `C:\AI\gpt-claude-mcp-bridge-v2` is changed. The existing uncommitted natural-shadow prompt correction remains a separate change and must be frozen before the first natural cohort receipt.

**Suggested execution model: Claude Opus.** This router changes the model-selection and answer-quality trust boundary, while the shadow/production audit split must preserve metric integrity. Advisory only; the user's chosen model remains valid.
